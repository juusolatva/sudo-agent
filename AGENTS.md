# AGENTS.md

Guidance and repository conventions for AI coding agents working on `sudo-agent`.

## Project Overview

`sudo-agent` is a lightweight, PAM-aware SSH agent daemon written in Rust for time-bound, human-approved `sudo` authentication. Instead of relying on static keys trusted indefinitely or re-typing passwords on every elevation, `sudo` challenges an SSH key held by this agent (via `pam_ssh_agent_auth`). The agent only signs authentication challenges if:
1. The key has not exceeded its configured Time-To-Live (TTL).
2. The user explicitly approves the signature request.

  - Shutdown: SIGINT/SIGTERM/SIGHUP end `run()` cleanly (keys cleared, socket removed). SIGINT while an approval prompt is open only denies it (`TerminalPrompter::interrupt()`; a deny *answer*, so routing withdraws the other backends); a second one within `STOP_WINDOW` (2 s) stops the agent anyway. The handlers are installed only after key loading, so Ctrl-C during passphrase entry keeps the default action, because echo is off at that point. `main` builds the runtime by hand and calls `shutdown_background()`, so exit never waits on a prompt blocked reading the terminal.
  - CLI (`src/cli.rs`): `sudo-agent serve [OPTIONS]`; the bare form `sudo-agent [OPTIONS]` is the same `ServeArgs` flattened at the top level, and options before `serve` are rejected. `sudo-agent approve [--control-socket PATH]` (`ApproveArgs`) is the approval client; `cli::parse` returns a `Run`.
  - Two sockets (`server::serve` runs both): `agent.sock` (`SudoAgent` → `Connection`: list + approval-gated sign; refuses and logs key management) and `control.sock` (`src/control.rs`: `ControlAgent` → `ControlConnection`, which reuses `Connection` and adds `ssh-add` add/remove with `keys::TtlPolicy`; uid check, `ssh` tripwire and `session-bind` refusal). `--control-socket` / `SUDO_AGENT_CONTROL_SOCKET`; same path for both, or a live agent on either, refuses to start.
  - Keys are added with `ssh-add` over `control.sock`, or loaded at startup via `--key <PATH>` (repeatable, optional) and `--ttl <DURATION>` (default `15m`, at most `--max-ttl`, default `8h`; a longer `--ttl` is a startup error), parsed with `clap`; encrypted keys prompt for the passphrase (3 attempts, empty aborts). Each key's TTL starts when it is decrypted, so with several `--key`s the deadlines differ. See `src/keys.rs`.
  - `KeyEntry` holds the decrypted `ssh_key::PrivateKey` (zeroized on drop by `ssh-key`) and an `expires_at` deadline on `CLOCK_BOOTTIME` (`keys::now()`), so suspend time counts against the TTL. Do not use `Instant` for TTLs (`CLOCK_MONOTONIC` pauses during suspend).
  - A background reaper drops expired keys every second; `request_identities()` also filters them.
  - `request_identities()` (shared by both sockets) lists each key's comment with its time left appended, `<comment> (14m30s left)` (`KeyEntry::listed_comment`, `keys::format_remaining`). Only the listing changes: the stored comment, prompts and log lines use the key's own comment.
  - `sign()` (`src/agent.rs`) looks up the requested key and checks its TTL under the lock, releases the lock, asks `Prompter::confirm()` (prompt errors count as denial), then re-locks and re-checks expiry before signing. Unknown/expired keys and unsupported requests are refused *before* prompting. Every approval/refusal is logged to stderr.
  - `SudoAgent` implements `Agent<UnixListener>` manually (not the clone-per-connection blanket impl) so each `Connection` records its peer via `SO_PEERCRED` (pid, uid, `/proc/<pid>/cmdline`). Peer-supplied text is passed through `sanitize()` before reaching the terminal; keep doing that for anything new shown in prompts.
  - RSA keys sign only with SHA-512 (`ssh-key` limitation), so RSA requests without the `rsa-sha2-512` flag are refused; Ed25519 is the recommended key type.
  - Only key types `ssh-key` can sign with (Ed25519, ECDSA, RSA) are accepted: `keys::unsignable` refuses the rest (security keys `sk-…`, DSA, unknown algorithms) in `keys::load` (before the passphrase) and in `ControlConnection::add`, and `sign()` checks it again before prompting, so no one approves a signature that would fail.
  - Approvals time out per backend: `--approval-timeout` (default `2m`) for the terminal prompt and `sudo-agent approve` clients, `--pinentry-timeout` (default `15s`, pinentry's own `SETTIMEOUT`) for the popup. The terminal prompt waits with `poll()` against a `keys::now()` (`CLOCK_BOOTTIME`) deadline and then gives up the terminal, so a stale read can't swallow the next prompt's answer. A timeout surfaces as an `ErrorKind::TimedOut` error from `confirm()`, logged as `not approved: no answer within …`. Durations for flags are parsed by `keys::parse_duration`.
  - Cancellation: `Prompter::confirm()` takes a `CancellationToken` and must withdraw the question (and only then return an error) once it fires. `sign()` cancels it when the client hangs up, detected by watching a duplicate of the client socket fd (`Connection::client`) with `AsyncFd` for read-closed (a request still queued behind another prompt just leaves the queue), or when the key expires (`SudoAgent::key_gone`). The reaper removes keys 250 ms after their deadline, so a withdrawn prompt's line ends before its log line. Ctrl-C on the remote `sudo` never reaches us: `sudo` ignores it while `pam_ssh_agent_auth` waits. `TerminalPrompter` polls a per-prompt wake pipe alongside the tty, and hanging up the pipe ends the wait. New backends must honour the token (pinentry: kill the child; approve client: drop the pending request).
  - Prompt abstraction (`src/prompt.rs`: `Prompter` trait + `TerminalPrompter`). The terminal asks startup passphrases directly; approvals go through `routing::Router` (`src/routing.rs`, held by `SudoAgent`), whose `ask()` asks every available backend (`Prompter::available()`) at once: the first `Ok` answer wins and the rest are withdrawn (cancelled and awaited); an `Err` is *no answer* (timeout, withdrawal, failure), and the request is denied only when every backend gave up or none is available. A lone backend's error passes through unchanged. The `Answer` names the backend (`by`), which log lines show (`Approved (pinentry) …`, `denied (terminal)`), and carries other backends' failures (not timeouts) the first time each happens, logged once by `sign()`. Backends: `terminal` (available if `/dev/tty` opened at startup) and `pinentry` (available if `DISPLAY` or `WAYLAND_DISPLAY` was set at startup; `--pinentry`, default `pinentry`; left out entirely with `--no-pinentry`) and `approve` (`src/approve.rs`: available while a `sudo-agent approve` is attached over `control.sock`; every attached client is shown each request; if all detach mid-request it waits 5 s for one to come back). The startup banner says which are in use (`approvals_line` in `main.rs`). Tests build a one-backend router with `Router::only`. Tests use `prompt::testing::{ScriptedPrompter, ApprovesAfter, GivesUp, Unavailable}`.

## Core Architectural Invariants

Agents modifying or extending this codebase must strictly preserve the following architectural principles:

1. **TTL Stays Inside the Agent**:
   - Do not rely on client-side `ssh-add -t`. Once keys can be added with `ssh-add`, a `-t` lifetime may *set* a key's TTL, but the agent itself tracks and enforces it. Cap policy (`TODO.md` → Background daemon): a lifetime above `--max-ttl` is clamped to it and logged, a key added without `-t` gets the default `--ttl`, so no key is ever without an expiry.
   - The expiration timer must be tracked inside `sudo-agent` so that key expiration status can be queried and surfaced remotely (e.g. warning remote users that a key is approaching expiry before or during `sudo`).
2. **Approval Prompt is Yes/No, Never Passphrase Re-entry**:
   - The key passphrase is required **once**, only when decrypting the key into agent memory at load time.
   - Per-signature approval is strictly a cheap confirmation (yes/no keypress). It serves as a sanity check and a detection mechanism against silent elevation (e.g. by another process reaching the socket). Requiring passphrases on every sign defeats usability.
   - Two accepted dependency advisories rely on every signature being approved by a person: the timing side channels in RSA signing ([GHSA-wwj9-h88v-6483](https://github.com/juusolatva/sudo-agent/security/advisories/GHSA-wwj9-h88v-6483), RUSTSEC-2023-0071) and ECDSA signing ([GHSA-rj9x-w6xp-x994](https://github.com/juusolatva/sudo-agent/security/advisories/GHSA-rj9x-w6xp-x994), RUSTSEC-2026-0387). Any change that weakens or bypasses approval (auto-approve, remembering approvals, unattended signing) must revisit them and the `.cargo/audit.toml` / `osv-scanner.toml` ignores first.
3. **Pluggable Prompt Abstraction with Terminal First**:
   - Design a single prompt abstraction supporting two kinds of interaction: secret input (passphrase at load) and binary confirmation (yes/no on sign).
   - Start with a terminal-based backend. It must remain functional even after other backends (GUI, desktop notifications) are introduced.
   - Planned backends: **pinentry** (desktop popup, spawned per request) and **`sudo-agent approve`** (terminal client on `control.sock`) are the focus. Once the approve client exists it is the terminal backend that must keep working; the daemon's own foreground prompt (today's `TerminalPrompter`) stays as a backup as long as it causes no problems.
   - Once the daemon loads keys via `ssh-add`, the passphrase part is the client's job; the daemon itself only ever asks yes/no.
4. **No Automated PAM Configuration Writing**:
   - Do not write automated PAM configuration mutators. Incorrect PAM modifications risk locking users out of root access on live systems, and PAM tooling differs across Linux distributions.
   - Setup must remain manual documentation (exact stanzas to paste) and non-destructive dry-run validation (`--check` flag).

## Planned Architecture (background daemon)

Agreed design for the "Background daemon" steps in `TODO.md` (settled 2026-10-12; details and rationale there). Keep new code compatible with it even before it lands:

- **CLI**: `sudo-agent serve` runs the agent; the bare form (`sudo-agent --key …`) stays an alias for `serve`. Other subcommands are clients over `control.sock`.
- **Two sockets, different trust.**
  - `agent.sock` is the forwarded one. It serves **only** `request_identities` and approval-gated `sign` (later at most a read-only status extension).
  - `control.sock` is never forwarded. It takes add/remove keys (later lock/unlock) plus our own vendor extensions (approve; later status, stop).
  - Never let `agent.sock` add or remove keys, lock or unlock, or answer approvals. Anything reachable through forwarding must be harmless to a hostile server.
  - Paths: separate flag and environment variable per socket (flag > env > default): `--agent-socket` (`--socket` kept as alias) / `SUDO_AGENT_SOCKET` (done in 1a), `--control-socket` / `SUDO_AGENT_CONTROL_SOCKET` (step 1b, through `socket::choose_path`; an empty variable counts as unset); defaults `agent.sock` / `control.sock` in the private runtime dir (`agent-<hostname>.sock` / `control-<hostname>.sock` in the cache-dir fallback).
- **`control.sock` protection, all three layers required**: (1) refuse a connection for good once it sends `session-bind@openssh.com` (it came through `ssh`); (2) peer uid (`SO_PEERCRED`) must equal ours; (3) tripwire: refuse when the peer's `/proc/<pid>/exe` is `ssh`. Log every refusal. The point is that an accidental `ForwardAgent …/control.sock` must not give a server control.
- **Keys are added from a client**: `ssh-add` over `control.sock`. The daemon starts with no keys, never prompts for passphrases, and restarting it drops them all (intended). Lifetime → TTL with the cap policy (invariant 1). `ssh-add -c` is accepted and ignored; `-h` (destination restriction) or any unknown constraint **refuses the key**; re-adding a loaded key replaces it and restarts its TTL.
- **Time left is shown in key comments** returned by `request_identities` on both sockets, as `<comment> (12m left)`, so `ssh-add -l` shows it on any server.
- **Approval routing**: every available backend (attached `approve` clients, pinentry, the foreground terminal) is asked at once; the first answer wins and the rest are withdrawn through their `CancellationToken`. Per-backend timeouts. No backend available: deny and log (a `serve` with neither a terminal nor a display can only be answered by `sudo-agent approve`, and says so at startup).
- **`approve` protocol**: vendor extensions on `control.sock` (long poll for the next event, request pending or withdrawn, from a per-connection queue; answer by id on a second connection), not a separate socket. Every attached client sees each request; the backend is available only while one is attached; it shares `--approval-timeout` with the foreground prompt. An answer's reply is `Success` only if it decided the request. The client reconnects when the daemon restarts (`TODO.md` → step 4).
- **Lifecycle**: one instance per user (`serve` refuses while either socket answers); systemd user service without socket activation (`contrib/systemd/sudo-agent.service`: `After=`/`PartOf=`/`WantedBy=graphical-session.target`, so it has the display for popups and drops the keys at logout), `setsid -f` fallback; timestamped log lines except under the journal (`JOURNAL_STREAM`); stop via signals/`systemctl` until `sudo-agent stop` exists. Closing a terminal never kills the daemon.
- **Later (agreed, after steps 0–4; don't start early)**: `sudo-agent stop`; **lock/unlock** (`ssh-add -x`/`-X`, on `control.sock` only; while locked every request is refused without a prompt); a read-only status extension plus `sudo-agent status`.

## Machines & Manual Testing

Work on this project happens on two kinds of machine, and an agent must know which one it is on:

- **Laptop (agent host)**: Fedora 44. Holds the private keys and runs `sudo-agent`. It has **no** `pam_ssh_agent_auth`: the module isn't packaged for Fedora 44, so `sudo` can't be tested here. Local testing uses `ssh-add -l` and `ssh-keygen -Y sign` against the socket.
- **Servers (sudo hosts)**: `pam_ssh_agent_auth` is already set up for `sudo`: `server-a` (openSUSE Tumbleweed, `pam_ssh_agent_auth` 0.10.4) and `server-b` (Debian, `libpam-ssh-agent-auth` 0.10.3). Their sudo timestamp timeout is zero, so every `sudo` authenticates. They hold **no private keys**; keys reach them only through the agent forwarded from the laptop (`ssh -o ForwardAgent=<sudo-agent socket>`). Do not try to run or load keys into `sudo-agent` on a server. `cargo build`/`cargo test` work there as usual.
- **Approval prompts appear on the laptop's terminal**, not in the server session. An agent on a server cannot see or answer them; ask the user to answer and relay what the prompt showed.
- **On a server, PAM and sudoers are read-only for agents.** Inspect (`/etc/pam.d/sudo`, the `file=` keys list, logs), then *propose* changes for the user to apply (`visudo`, with a root shell kept open). Never edit them, and never run `sudo` in a way that could change them. This extends invariant 4 below to manual testing.
- Full step-by-step procedure, test matrix and troubleshooting: `docs/manual-e2e.md`.

## Project Structure

- `Cargo.toml`: Package definition and dependencies (`ssh-agent-lib`, `ssh-key`, `tokio`, `async-trait`, `clap`, `libc`, `rpassword`, `signature`, `socket2`, `tokio-util` (`CancellationToken`), `zeroize`; dev: `tempfile`; `ssh-key` with `crypto` + `encryption`).
- `src/cli.rs`: Command line (clap): `serve` subcommand, bare-form alias, `ServeArgs`, `--ttl`/`--max-ttl` check.
- `src/main.rs`: Entry point: startup key loading, the expiry reaper, signal handling (Ctrl-C denies an open prompt), and the listener loop; `approve()` sets up the client (socket path, terminal, signals) for `approver::attend`.
- `src/agent.rs`: `SudoAgent` (per-connection `Agent` factory) and `Connection` (implements `Session`: identities + approval-gated `sign()`, withdrawing the prompt on client hang-up or key expiry), peer identification, and prompt sanitizing.
- `src/logging.rs`: `log!`'s line formatting: the local timestamp (`localtime_r`) and the journal check.
- `src/keys.rs`: `KeyEntry`, the `CLOCK_BOOTTIME` clock, key loading/decryption, expiry purging, and TTL parsing/formatting.
- `src/pinentry.rs`: `Pinentry` backend: spawns `pinentry` per request in its own session (`setsid`, `PR_SET_PDEATHSIG`), speaks Assuan (`SETPROMPT`/`SETDESC`/`SETOK`/`SETCANCEL`/`SETTIMEOUT`/`CONFIRM`); only the cancel error (99) is a denial; withdrawal is SIGTERM, then SIGKILL after 1 s. Tests use a fake `sh -c` pinentry; `real_pinentry_*` are `#[ignore]`d manual tests.
- `src/approve.rs`: `ApproveClients`, the `sudo-agent approve` clients as one approval backend (available while one is attached; every client is shown each request), each connection's coalescing `Events` queue, and the wire format of the `approve-wait@…`/`approve-answer@…` extensions (`Event`, `Reply`), served by `ControlConnection::extension`.
- `src/approver.rs`: The `sudo-agent approve` client (`attend`): one connection waiting for events (read in a background task), a connection per answer, one `TerminalPrompter` prompt at a time, reconnecting when the daemon goes away. Tests use a scripted fake daemon (`ssh_agent_lib::agent::listen` on a `Session`).
- `src/routing.rs`: `Router`, the approval `Prompter` that asks every available backend at once (first answer wins).
- `src/prompt.rs`: `Prompter` trait (secret input + yes/no confirm + availability) and the `/dev/tty` `TerminalPrompter` backend. Prompts are serialized; approval requires typed `y`/`yes` + Enter and discards type-ahead first. `confirm()` is cancellable (`CancellationToken`, a wake pipe polled next to the tty); `TerminalPrompter::interrupt()` serves Ctrl-C.
- `src/control.rs`: `control.sock`: `ControlAgent`/`ControlConnection` (key add/remove for `ssh-add`, TTL policy, constraint rules) and the three forwarding protections (`refusal`, `session-bind` in `extension`).
- `src/server.rs`: `serve()`: runs `agent.sock` and `control.sock` until shutdown with its own accept/frame loop (not `ssh_agent_lib::agent::listen`, which has no limits): per-socket `Limits` (connection cap, 256 KiB frame limit checked before buffering, idle and incomplete-frame timeouts; `control.sock` may idle), and descriptor/memory exhaustion in `accept()` is retried, not fatal. Also the socket-level tests (real `socket::bind`, driven by `ssh_agent_lib::client::Client`).
- `src/socket.rs`: Socket path selection (XDG runtime dir with cache-dir fallback), private-directory checks, stale-socket handling, and binding.
- `contrib/systemd/sudo-agent.service`: The systemd user unit (`~/.cargo/bin/sudo-agent serve`, tied to `graphical-session.target`); not in the crate package.
- `docs/manual-e2e.md`: Manual `pam_ssh_agent_auth` end-to-end test procedure (laptop agent ↔ forwarded server `sudo`).
- `TODO.md`: Detailed roadmap (Now, Next, Someday) and in-depth rationales for core design decisions.
- `.github/workflows/build.yml`: CI on pushes to `main` and PRs: `cargo fmt --check` + Clippy (`-D warnings`), and SonarQube, which is also where the tests run (coverage from `cargo llvm-cov` → `lcov.info`; `sonar.qualitygate.wait=true` in `sonar-project.properties`, so a failed quality gate fails the job). PRs from forks get no `SONAR_TOKEN`, so they skip the SonarQube steps (`SONAR_ANALYSIS`) and only run the tests.
- `.github/workflows/security.yml`: `cargo audit --deny warnings` and `cargo deny --locked check bans licenses sources`, on pushes, PRs and daily (new advisories against an unchanged `Cargo.lock`).
- `.github/workflows/osv-scanner.yml`: Google's OSV-Scanner reusable workflows (`scan-scheduled` on pushes to `main` and weekly schedule uploading SARIF to Code Scanning; `scan-pr` on PRs and merge groups failing on newly introduced vulnerabilities).
- `.github/dependabot.yml`: weekly version-update PRs for Cargo dependencies and the workflows' actions (7-day cooldown, minor/patch grouped). Not covered: the `tool:` versions given to `taiki-e/install-action` and the `stable` toolchain. Actions are pinned by full commit SHA with a `# vX.Y.Z` comment; keep that form when editing workflows. Dependabot PRs get only Dependabot secrets, so `SONAR_TOKEN` must be one too or their SonarQube job fails.
- Outside the repository (GitHub settings): CodeQL default setup (Rust + Actions, on pushes and weekly), Dependabot alerts and security updates.
- `deny.toml`: cargo-deny config (Linux targets, license allow-list, crates.io only, no wildcards). Advisories are left to cargo-audit.
- `.cargo/audit.toml` and `osv-scanner.toml`: cargo-audit and OSV-Scanner ignores, kept in sync with their reasons (currently RUSTSEC-2023-0071, `rsa` via `ssh-key`, and RUSTSEC-2026-0387, `crypto-bigint` 0.5 via `ssh-key`'s ECDSA curves; see `TODO.md` → Other).

Don't silence findings to get green: a new license goes into `deny.toml`'s allow-list, and an advisory into `.cargo/audit.toml`'s `ignore` and `osv-scanner.toml`'s `[[IgnoredVulns]]`, only with the user's agreement and a comment/reason giving the rationale. The `syn` duplicate warning from `cargo deny` (2.x via `curve25519-dalek-derive`, 3.x elsewhere) is known and harmless. A full `cargo deny check` also reports RUSTSEC-2023-0071 and RUSTSEC-2026-0387, because cargo-deny doesn't read `.cargo/audit.toml`.

- **After `cargo publish` / `cargo package`** (even `--dry-run`), run `cargo clean -p sudo-agent`. Packaging rewrites the dev binary's fingerprint to track `target/package/…/src`, after which `cargo build` silently reuses a stale `target/debug/sudo-agent` (tests are unaffected, so it looks like code passes tests but fails when run).

## Coding Conventions & Guidelines

- **Rust Edition & Idioms**: Target Rust 2024 edition. Use idiomatic Rust error handling, integrating with `ssh_agent_lib::error::AgentError`.
- **Async Runtime**: Built on `tokio` (multi-threaded runtime). No blocking file I/O inside `async fn`s: use `tokio::fs` or `spawn_blocking` (SonarQube rule `rust:S7493`). `SudoAgent` implements `ssh_agent_lib::agent::Agent<UnixListener>`; `listen()` calls its `new_session()` for each accepted socket, which returns a `Connection` (the `Session`) sharing the key store and prompter. `SudoAgent` must not implement `Session` itself, or it would collide with `ssh-agent-lib`'s clone-per-connection blanket impl.
- **Concurrency & Locking**: Keys in `SudoAgent` are guarded by an `Arc<Mutex<Vec<KeyEntry>>>`. Keep mutex lock guards scoped as tightly as possible; never hold locks across async points or while waiting for user interaction/prompt approval. The one deliberate exception is `SudoAgent::requests` (a fair `tokio::sync::Mutex<()>`), held for a whole `sign()` so requests are served one at a time in arrival order; it guards no data, only the user's attention.
- **Terminal output**: Anything printed while requests are served goes through the `log!` macro (`src/main.rs`), not `eprintln!`: it writes the whole line in one `write()`, so it can't split a prompt (which is also written in one `write()`). It also starts each line with a local timestamp (`src/logging.rs`), left out when stderr is the journal (`JOURNAL_STREAM` matching stderr's `dev:ino`). Use it for all output, startup banner and final error in `main` included; only prompts and their answers (passphrase entry, `Wrong passphrase, try again.`) stay plain. A message must not start with `\n` (it would land after the timestamp); write the newline separately first, as the SIGINT line does.
- **Testing**: Unit tests live next to the code (`#[cfg(test)] mod tests`); socket-level tests (whole agent on a temp socket, real client) live in `src/server.rs`. Shared helpers: `keys::testing::entry` (random Ed25519 `KeyEntry`), `keys::testing::security_key` / `opaque_key` (keys we can't sign with), `prompt::testing::ScriptedPrompter` (scripted answers) and `ApprovesAfter` (approves after a delay unless cancelled). Pin every refusal at the protocol level (`Client::handle` → `Response::Failure`), not just `is_err()`. Never commit private keys as fixtures: generate them at test time (`PrivateKey::random(&mut OsRng, …)`) into a `tempfile::tempdir()`. Generating RSA keys in debug builds is slow; test RSA-specific logic without a real RSA key (see `agent::tests::rsa_needs_sha512_flag`).
- **Secret scanning**: The user's pre-commit hook runs `betterleaks` and should stay strict. Silence a false positive with an inline marker on the flagged line, `# betterleaks:allow (<reason>)` (see `rpassword` in `Cargo.toml`), rather than loosening the scanner.
- **Git & Commits**: Commits are allowed, and pull requests on feature branches are preferred over pushing directly to `main`.
